# Mises à jour depuis une fiche projet

## Parcours utilisateur

La priorité du moteur est **zéro vulnérabilité connue signalée dans le périmètre contrôlé**, puis les versions stables les plus récentes parmi les combinaisons admissibles et réellement validées. Une version plus récente vulnérable ne peut pas être retenue au détriment d’une version sûre compatible. Une recherche bornée épuisée signifie « aucune combinaison sans faille validée dans cette recherche », jamais « aucune solution n’existe ». Les limites de couverture, notamment les systèmes d’images gérées par l’hébergeur qui ne sont pas analysés, restent explicitement signalées ; aucun résultat ne garantit l’absence de faille inconnue.

Un bouton **Tout mettre à jour** lance les services admissibles de la fiche. La progression et le résultat restent sur cette fiche ; les sources, les erreurs détaillées, les sauvegardes et les références de récupération sont repliées. Un double clic réutilise le même traitement. Les services hors périmètre restent identifiés dans les détails et leur nombre est affiché : le bouton ne prétend pas les mettre à jour.

Il n’y a ni PR à approuver, ni fusion manuelle. Les montées majeures des dépendances directes sont incluses lorsqu’elles sont compatibles. Node cible la dernière LTS encore maintenue, pas une version « Current » non LTS. Vigie recherche un ensemble de versions stables en tenant compte des moteurs Node et des dépendances homologues (`peerDependencies`) des versions candidates, pas seulement des versions déjà installées. Un parseur qui exige TypeScript inférieur à 6.1 conduit ainsi à sélectionner le TypeScript stable admissible le plus récent, plutôt qu’à imposer TypeScript 7 ou à bloquer les autres paquets. Les préversions, versions dépréciées et versions supérieures au dist-tag `latest` sont exclues ; les versions ne sont pas ramenées sous le minimum déjà déclaré. Les versions retenues pour compatibilité sont expliquées dans les détails.

La recherche est déterministe et bornée ; lorsqu’il existe plusieurs ensembles incomparables, elle choisit un ensemble valide en privilégiant les versions récentes, sans prétendre à un optimum mathématique unique. Les paquets dépréciés ou références locales/privées particulières sont conservés avec un avertissement. Les dépendances transitives sont résolues par le gestionnaire ; npm et pnpm doivent accepter strictement les pairs, sans `--force` ni `--legacy-peer-deps`. La compatibilité des déclarations ne prouve pas la compatibilité du code : installation, typage, tests et construction restent obligatoires avant publication.

La version Node testée est écrite **exactement** dans `engines.node`, ainsi que dans `devEngines.runtime.version` lorsqu’il est déclaré. Les fichiers `.nvmrc` et `.node-version` déjà présents sont également actualisés avec ce correctif exact. Une plage telle que `24.x` ne garantit pas qu’un hébergeur utilisera le correctif de sécurité testé. Un forçage Railway `RAILPACK_NODE_VERSION` imprécis ou différent est refusé avant publication ; aucune variable de l’hébergeur n’est réécrite silencieusement.

Si le compilateur identifie une rupture d’API dans un paquet direct nouvellement monté de majeure, Vigie peut retenir la dernière version compatible de sa branche actuelle et refaire toute la validation, tout en conservant les mises à jour indépendantes. Les options TypeScript supprimées ou dépréciées bloquant le compilateur sont également reconnues. Ce repli est limité à trois essais pour le groupe de services ; un échec métier sans cause identifiable n’est jamais ignoré. Avant chaque essai, Vigie vérifie que les scripts n’ont altéré ni le code ni les manifestes/verrous validés. Les journaux bruts ne sont pas renvoyés dans l’application.

Pour npm, le verrou est recalculé dans le répertoire temporaire à partir des manifestes exacts retenus, plutôt que de réutiliser un ancien arbre contradictoire. Ce n’est pas une suppression du verrou publié : un nouveau verrou complet, puis une installation `npm ci` stricte et les tests, sont obligatoires. Le verrou précédent reste dans l’ancien commit ou la sauvegarde des sources.

Le backend NesAppli dispose d’un profil de test reconnu par son manifeste et son schéma de configuration : ses tests reçoivent uniquement des valeurs factices explicites, avec Supabase et SMTP pointant sur le port fermé 9 de la boucle locale du conteneur. Aucun accès ni secret de production n’est utilisé ; les appels aux services doivent être simulés par les tests du projet. Ce profil n’est jamais publié dans les sources et ne change pas la configuration Railway. Si les tests ont besoin de vrais services ou d’une autre configuration, la validation échoue : leurs assertions ne sont ni ignorées ni désactivées.

## Applications avec GitHub

### Contrôles de sécurité automatiques

Le bouton reste unique. L’exécuteur utilise **OSV-Scanner 2.7.0** pour les fichiers de verrouillage npm/pnpm/Yarn, avant modification puis après résolution des versions candidates, **avant les scripts de validation**. Les manifestes et verrous sont copiés seuls dans un répertoire temporaire sans configuration du projet : un fichier `.osv-scanner.toml` fourni par les sources ne peut pas supprimer des alertes. Les rapports JSON doivent couvrir tous les verrous attendus ; erreur réseau, outil absent, rapport invalide ou analyse incomplète arrêtent la publication. Le code de sortie OSV 1 (vulnérabilités détectées) est interprété, pas assimilé à une panne ni ignoré.

**Trivy 0.76.1** analyse la base runtime originale des Dockerfiles admis, puis l’image finale réellement construite avant son démarrage de contrôle. La base seule n’inclut pas le code de l’ancienne application : cette limite de comparaison est indiquée dans le rapport. La nouvelle image inclut ses paquets système et applicatifs détectables. Une distribution candidate en fin de support ou non identifiée bloque ce parcours ; la fin de support de l’ancienne base est signalée sans empêcher sa correction. Les images finales fabriquées par Railpack/Vercel ne sont pas récupérées : les dépendances sont contrôlées par OSV, mais leur système final reste explicitement non analysé par Trivy.

Les outils sont téléchargés depuis leurs dépôts officiels, avec versions et empreintes SHA-256 fixées dans `scripts/install-update-scanners.ts`. Ils ne reçoivent ni secrets de production, ni jetons de déploiement. Les bases de vulnérabilités sont consultées à chaque traitement, sans mode hors ligne périmé ni exclusion des failles sans correctif. OSV peut transmettre les identifiants/versions des dépendances à son service ; Trivy interroge ses bases et les registres d’images publics. Les rapports conservés contiennent uniquement références d’alertes, noms, versions, sévérités, périmètre et date ; les journaux bruts ne sont pas renvoyés.

Politique de publication :
- Toute vulnérabilité signalée dans la candidate ou après installation bloque la validation, quelle que soit sa sévérité, y compris si elle était déjà présente ou qu’aucun correctif n’est publié. L’état initial sert à identifier les corrections à chercher, jamais de liste d’exceptions.
- Une alerte OSV sur un verrou npm déclenche la recherche de correctifs indirects et de parents compatibles ; une alerte Trivy déclenche les autres variantes d’image admises. Les réserves de couverture ou de tests métier ne dispensent jamais de corriger une vulnérabilité connue. Un dernier garde avant le statut global terminé refuse également les anciens résultats permissifs contenant encore des alertes.
- Après un repli de compatibilité, le nouveau verrou est à nouveau analysé : le repli ne peut pas contourner la sécurité.
- Les scripts `test:integration` et `test:e2e`, lorsqu’ils existent, sont exécutés automatiquement après le build en plus du typage et des tests habituels. Le projet doit fournir son environnement de test et ses assertions, par exemple une configuration Playwright avec démarrage du serveur et navigateurs disponibles. Un script absent est signalé ; aucun test métier ou navigateur n’est inventé ni marqué comme réussi.

Ces contrôles ne créent pas encore une préproduction complète chez l’hébergeur, ne prouvent pas l’absence de faille inconnue et ne constituent pas une surveillance planifiée entre deux clics. Socket, Renovate et un délai de recul sur les nouvelles publications ne sont pas activés par cette intégration. Les détails des contrôles sont repliés dans le suivi de chaque service ; le résultat global signale les réserves.

### Boucle de correction des dépendances indirectes

Une alerte OSV bloquante sur un projet npm déclenche désormais une recherche de correction, au lieu d’arrêter immédiatement la préparation :

1. OSV propose des changements `in-place` sur une copie du verrou, avec `--no-introduce`, sans exécuter les scripts ni lire les configurations ou secrets du projet. Ces propositions sont expérimentales et ne sont jamais considérées comme une preuve de compatibilité.
2. Vigie vérifie le graphe npm : aucune dépendance directe modifiée silencieusement, aucune nouvelle préversion, origines npm publiques avec intégrité vérifiable (y compris si seul l’artefact change, à version identique), et respect des contraintes déclarées des parents. Une proposition hors contraintes est rejetée dans la copie privée, puis la recherche passe aux parents. Aucun nouvel `override`, aucune suppression d’alerte, aucun `--force` npm ni `--legacy-peer-deps` permissif n’est ajouté.
3. Le verrou proposé doit passer `npm ci --ignore-scripts --strict-peer-deps --legacy-peer-deps=false --force=false`, puis `npm ls --all --json`. Une proposition refusée est abandonnée, le verrou candidat précédent est restauré et la recherche passe aux parents ; une erreur d’outil ou un délai dépassé n’est pas présenté comme une correction.
4. Quand plusieurs versions d’un parent indirect coexistent sur une chaîne vulnérable, le moteur tente de coordonner le verrou avec `npm dedupe --package-lock-only --ignore-scripts --prefer-dedupe` et les mêmes options strictes. Le résolveur npm cherche une version commune satisfaisant les déclarations des consommateurs, plutôt que de conserver une version récente vulnérable à côté d’une version compatible. Le manifeste et les versions directes restent figés. Le graphe proposé doit passer les contrôles d’origine, d’intégrité et de contraintes, puis l’installation stricte sans scripts, `npm ls` et un nouveau scan OSV. Une coordination refusée est restaurée ; une même proposition de graphe n’est pas retentée indéfiniment. Cette coordination concerne uniquement la racine affectée.
5. Si le verrou seul ne suffit pas, le graphe remonte jusqu’aux dépendances directes concernées, y compris par les dépendances homologues. Les catalogues npm et l’API OSV permettent de chercher des versions stables du paquet vulnérable et des parents pouvant les accepter. Toutes les alertes sont regroupées par parent : jusqu’à huit versions admissibles, choisies des plus récentes aux plus anciennes dans les catalogues bornés, sont proposées ensemble au résolveur de pairs. Une version non sélectionnée n’est pas marquée comme déjà essayée. Les chemins vulnérables déjà observés restent en mémoire pendant l’exécution. Un parent candidat peut être antérieur au dernier publié, voire à celui du verrou initial uniquement dans la plage déjà déclarée ; la proposition est signalée et reste soumise à tous les contrôles.
6. Toute nouvelle proposition est résolue, réanalysée par OSV, puis soumise à l’installation figée, aux tests et au build. Si les tests refusent une proposition de parent sécurisé, celle-ci est marquée essayée et une autre combinaison peut être recherchée ; les assertions ne sont jamais ignorées. Les vérifications Docker/Trivy et du déploiement restent ensuite obligatoires.

Les tentatives de correction du verrou sont rattachées à la combinaison complète des versions directes proposées. Si un autre service doit conserver une branche compatible après échec de ses tests, sa nouvelle combinaison peut refaire la coordination indirecte nécessaire, avec une nouvelle installation stricte et un nouveau scan. Le suivi signale ce repli dès son déclenchement ; il ne réutilise aucune approbation de sécurité précédente.

Un échec de validation sans paquet direct identifié peut aussi provenir d’une rupture entre versions indirectes pourtant admises par leurs plages. Vigie extrait au fil de la sortie les noms et emplacements npm autorisés dans le graphe, même si le journal dépasse sa limite de conservation. Les chemins système et journaux bruts ne sont pas exposés. L’emplacement exact évite de modifier une autre copie du même paquet, installée pour une branche différente.

Le moteur explore alors les versions stables publiques des paquets impliqués, avec leurs artefacts et leur intégrité. Les fournisseurs de pairs sont prioritaires. Si un consommateur indirect empêche le changement, ses versions de référence peuvent être coordonnées dans la même proposition ; leurs déclarations ne sont jamais réécrites. La résolution native peut ajouter les copies imbriquées nécessaires aux dépendances ordinaires. Les versions directes restent figées et le graphe final doit satisfaire toutes les contraintes, les pairs stricts, les origines et l’intégrité. Chaque proposition passe un nouveau scan avant les scripts, puis l’installation figée, le typage, les tests et le build. Une ancienne version vulnérable ne bénéficie d’aucune exemption.

Cette recherche examine au plus quarante versions par paquet, en privilégiant le dernier correctif admissible de chaque branche mineure, et six propositions par racine. Elle sonde les intervalles puis se rapproche des versions récentes qui passent ; ce n’est pas une preuve d’optimalité globale ni une recherche exhaustive des incompatibilités non monotones. Le meilleur verrou effectivement validé est vérifié une dernière fois avant d’être retenu. Une erreur d’outil, une analyse incomplète ou une altération des sources arrête le parcours. Quand aucune recherche par catalogue n’est possible, un repli ciblé vers les versions initiales ou une résolution depuis le verrou initial restent soumis aux trois reprises de validation existantes. Aucun de ces replis ne modifie le code de l’application ou les options du compilateur.

Un refus npm `ERESOLVE` pendant la résolution sans scripts peut aussi révéler un pair indirect absent des métadonnées directes. Vigie extrait uniquement les noms, versions et plages du conflit, confirme la déclaration du consommateur dans le catalogue npm public, puis recalcule les versions directes ensemble. Les contraintes apprises sont attachées à la proposition de parents et aux limites de validation concernées ; elles ne sont pas réutilisées pour une autre proposition. Si leur intersection ne permet aucun ensemble admissible, la proposition de sécurité est écartée et la recherche reprend sur les parents. Les bornes initiales, les installations strictes et tous les contrôles restent actifs. Huit reprises de résolution au maximum sont autorisées ; les journaux bruts ne sont pas exposés dans le suivi.

La recherche est bornée : six propositions de sécurité, quarante versions stables par paquet lors de la recherche des parents, et les trois replis de validation existants. Des empreintes de candidats et une liste des choix essayés empêchent les boucles sans progrès. Un arrêt signifie qu’aucun ensemble validé n’a été trouvé dans ce périmètre, pas une preuve mathématique qu’aucune combinaison n’existe.

Cette remédiation automatique concerne pour l’instant les verrous npm v2/v3 (`package-lock.json` et `npm-shrinkwrap.json`), avec ou sans Git. pnpm/Yarn restent analysés et bloqués en cas de risque, mais leur remédiation indirecte n’est pas inventée : leurs graphes nécessitent une intégration dédiée. Les liens locaux, workspaces et sources particulières restent hors de cette recherche.

Pour la documentation NesAppli, Docusaurus 3.10.2 exige `tinypool ^1.0.2`. Les correctifs actuellement vérifiés sont sur la branche 2.x. Si aucun parent stable admis ne permet cette branche, la préparation reste bloquée et indique la chaîne exacte ; forcer tinypool 2.x dans une dépendance qui exige 1.x ne constitue pas une compatibilité démontrée.

Le pilote isolé du 23 octobre 2026 a effectivement recalculé React et React DOM en 18.3.1 après le refus d’un pair indirect de Docusaurus 3.7. Cette proposition a ensuite été refusée par OSV (`node-forge` et `tinypool`). La recherche commune aux alertes a produit une autre proposition, de nouveau résolue et analysée, mais `tinypool 1.1.1` restait bloquant. Aucun ensemble validé n’a été trouvé dans la recherche bornée : les tests/builds de NesAppli et les contrôles Docker/Trivy candidats n’ont pas été atteints, et aucune publication n’a été effectuée. Ce pilote ne valide donc pas une mise à jour de NesAppli.

La vérification isolée du 27 octobre 2026, sur le commit `9ead4d5f4c59f643842eca1b77c8b1d77227c693`, a ensuite validé les propositions du moteur avec Node 24.22.1. La coordination indirecte retire tinypool du verrou de la documentation et retient Webpack 5.104.1 avec schema-utils 4.3.3 après les essais de compatibilité. Les verrous des trois services ont été repris mécaniquement, sans nouvelle résolution ni choix manuel de version : installation stricte, tests/builds du frontend et du backend, et build de la documentation réussissent ensemble. Le scan OSV ne comporte aucun blocage. Les bases Debian refusées par Trivy sont écartées ; pour ce Dockerfile portable, le moteur construit puis valide l’image Node Alpine officielle, sans modifier les instructions applicatives. Le scan final conserve quinze alertes non bloquantes, la version Node réelle est contrôlée, `/healthz` répond et la documentation sans session reste refusée. Les sources de l’image correspondent au verrou testé. Cette vérification s’est déroulée en phases et ne revendique ni publication ni déploiement en production ; aucun code, script de test ou contrôle de sécurité de NesAppli n’a été adapté pour la faire passer.

Le traitement lit la branche de production et les répertoires effectivement rattachés au projet. Les services d’un même dépôt sont regroupés pour ne publier qu’un commit. Le dépôt entier est verrouillé, y compris s’il est partagé entre plusieurs fiches. Une publication sur une branche reliée à plusieurs hébergements peut naturellement déclencher leurs déploiements automatiques : les filtres de construction doivent être configurés chez les hébergeurs.

Les sources du dernier commit sont extraites dans un répertoire temporaire. Les manifestes et fichiers de version de Node sont actualisés, puis le gestionnaire résout un nouveau verrouillage. L’installation figée, le typage, les tests et la construction déclarés sont exécutés dans des conteneurs Docker limités, non privilégiés, sans les jetons GitHub/hébergeurs, la clé de chiffrement ni l’URL de base Vigie. Au moins un script `test` ou `build` est nécessaire. Les secrets de production ne sont pas fournis aux tests.

Une modification du code par les scripts, ou une modification des manifestes/verrous pendant les tests, annule la publication. La référence Git est avancée sans force, avec le commit testé comme parent : une modification concurrente n’est jamais écrasée. Les règles de protection GitHub ne sont pas contournées. Si la branche exige une PR, l’exécution directe ne peut pas publier sur cette branche.

Les Dockerfiles Node standard placés à la racine effective du service sont pris en charge, y compris les images multi-étapes : toutes les bases officielles `node:VERSION-VARIANTE` sont actualisées en préservant initialement leur variante, ainsi que les paquets explicitement installés par une instruction npm simple. Un paquet runtime également présent dans le manifeste reçoit la même version compatible. Les instructions ne sont pas réécrites. Avant publication Git, les modifications du Dockerfile sont comparées au fichier du commit source : seuls les versions et les changements de base officielle autorisés ci-dessous peuvent changer.

Si Trivy refuse une image Debian pour une alerte bloquante, Vigie essaie les variantes officielles Trixie puis Bookworm, à version Node identique, en coordonnant toutes les étapes et en conservant le format complet ou `slim` de chacune. Si toutes les bases sont minimales et si le Dockerfile ne contient que des instructions portables reconnues (copies, commandes npm, démarrage Node et configuration standard), une variante Alpine officielle peut aussi être testée. Les commandes système, shells personnalisés et configurations particulières excluent ce repli ; une image complète n’est pas convertie en image minimale, et Alpine n’est pas converti en Debian. Au maximum quatre images distinctes sont construites ; chaque image doit repasser Trivy, le contrôle de la version Node et le démarrage HTTP. Le build applicatif doit fonctionner dans l’image choisie, y compris les dépendances natives éventuelles. Aucun identifiant de vulnérabilité n’est exclu. Une erreur de construction, d’outil ou de démarrage interrompt la préparation ; si toutes les variantes sont refusées, le Dockerfile candidat initial est restauré et la préparation échoue.

L’image est reconstruite à partir des seuls fichiers sources et verrous autorisés, sans artefacts des tests ni secrets du worker. Elle doit démarrer sous le Node demandé et répondre à un contrôle HTTP local dans un conteneur sans réseau externe, à capacités supprimées et racine en lecture seule. Pour la documentation NesAppli protégée par SSO, seules des valeurs de configuration factices sont utilisées ; `/healthz` doit répondre et la racine sans session doit rester refusée. Cela ne remplace pas un test du SSO réel. Le Dockerfile historique de NesAppli installe son paquet runtime avec une version directe explicite mais sans verrouillage transitif dédié ; ce comportement n’est pas transformé silencieusement en un autre mode de construction.

Vigie attend le déploiement automatique du commit exact chez Vercel/Railway, son activation en production, puis un contrôle HTTPS public. Un ancien déploiement prêt n’est pas une preuve de réussite. Les déploiements automatiques Git doivent donc être activés. Les anciennes références de commit et de déploiement restent enregistrées ; aucune base applicative n’est restaurée automatiquement.

Avant de déclarer un service terminé, un contrôle **Node après installation** vérifie le déploiement, le commit, le dépôt/la branche et l’empreinte de l’image active. Pour un runtime Railway, y compris les Dockerfiles auto-détectés sous un builder configuré `RAILPACK`, une sonde SSH lit Node installé et les exécutables des processus Node applicatifs déjà lancés dans chaque instance. Elle n’importe pas l’application et désactive les préchargements Node. Les identités du service, de l’environnement et du déploiement doivent correspondre ; la liste des instances et l’image active sont relues après la sonde. Une coexistence de déploiements, une version différente (même plus récente), un changement d’instances ou une preuve absente bloque le contrôle. Pour un site statique Railpack, le manifeste atteste seulement Node utilisé lors de la construction ; il ne prouve pas un runtime Node dans le serveur statique.

La sonde utilise une clé SSH éphémère créée puis révoquée dans le workspace Railway ; sa clé privée reste dans un répertoire temporaire de l’exécuteur, hors des montages de test. Une révocation non confirmée bloque le contrôle. L’accès à la sonde est testé avant les installations et toute publication. Un tag Docker, un test d’image locale ou le seul HTTP 200 ne remplacent jamais cette lecture. Une vérification en échec n’empêche pas de recueillir les preuves des autres services ; l’exécution globale reste **À vérifier**. Vercel, qui ne fournit pas ici de preuve du correctif exact exécuté, conserve également ce statut. Aucun ancien succès ni fichier inchangé ne dispense de la vérification ; les références et verrous sont conservés et les historiques antérieurs ne sont pas réécrits.

Pour limiter les reprises coûteuses, les scans OSV inchangés sont réutilisés pendant moins de cinq minutes dans la même exécution, en conservant leurs alertes et leur date réelle. Tout manifeste ou verrou modifié est rescanné ; une analyse fraîche de tous les verrous reste obligatoire avant publication. Trivy partage sa base dans le job sans désactiver sa mise à jour. Les essais indirects ne réinstallent plus deux fois le même arbre npm : l’installation stricte et `npm ls` précèdent les tests. Une validation réussie peut être réutilisée seulement pour les mêmes sources de tout le dépôt, verrous, scripts, profil et version Node ; aucun échec n’est mis en cache. Un service ayant échoué est testé en priorité lors du repli suivant, avant de refaire les autres validations.

Dans un même dépôt, les services standard indépendants sont préparés en parallèle, au maximum deux à la fois et selon les CPU/mémoire disponibles. Chaque service possède sa copie complète des sources, ses verrous, ses contraintes de pairs et ses budgets de reprise : un refus dans le backend ne relance pas la préparation du frontend. Les racines imbriquées, dépendances locales et configurations de workspaces conservent le traitement coordonné et ses restrictions existantes. L’image Node des sandboxes est figée par son identifiant pour toute l’exécution ; elle entre dans la signature des validations réutilisables. Les scans Trivy restent sérialisés pour protéger leur cache partagé.

Après préparation, seules les modifications de versions autorisées sont assemblées dans une copie intermédiaire. Chaque service revalide cette proposition complète, dans une copie fraîche, après son contrôle de sécurité ; un résultat antérieur n’est réutilisé que si toutes les entrées et l’image de validation correspondent exactement. Cela couvre aussi les lectures de fichiers voisins non déclarées comme dépendances locales. Les images Docker déjà construites, scannées et démarrées sont conservées comme preuves seulement pour leur contexte de construction inchangé. Aucune modification n’est transférée aux sources à publier tant que tous les contrôles de l’ensemble n’ont pas réussi. Une erreur attend l’arrêt des tâches déjà lancées avant de nettoyer leurs répertoires ; le scan final frais, les contrôles avant publication et les attestations Node après déploiement restent obligatoires.

### Configuration déjà validée

Seules des références établies avec l’objectif strict et des signatures de sécurité vides sont réutilisables. Les anciennes références autorisant des failles sont invalidées. Le raccourci refait les scans et ne peut pas réutiliser une combinaison vulnérable inchangée. Les versions indirectes sont essayées des plus récentes aux plus anciennes, sans déduire une incompatibilité de toutes les versions supérieures de l’échec d’une version intermédiaire ; plusieurs correctifs d’une même branche peuvent être examinés. Les limites d’essais coûteux restent actives.

Avant de rechercher de nouvelles combinaisons, le moteur cherche une validation réussie de moins de 24 heures pour les mêmes sources complètes, services, version Node et politique de validation. La référence inclut les verrous, scripts, profils, code du moteur, outils configurés, image du runner et empreintes officielles des images Node de tous les stages Docker. Les traitements en échec ou « À vérifier » ne fournissent aucune référence réutilisable. Une reprise conserve la date originale de validation et les réserves ; elle ne prolonge pas sa validité.

Les catalogues npm sont revérifiés, y compris ceux des dépendances indirectes et des propositions écartées. Les catalogues complets sont comparés par ETag ; la réponse `/latest`, qui ne fournit pas toujours cet en-tête, est comparée par empreinte de son contenu borné. Une publication sur une autre branche du paquet invalide également la référence. Une modification en cours de résolution, une couverture trop grande ou une attestation de catalogue/image indisponible empêchent ce raccourci sans transformer une mise à jour réussie en échec.

Si tout correspond, seuls la recherche de versions, les installations de qualification et les scripts déjà réussis sont évités. OSV refait une analyse fraîche de tous les verrous ; les Dockerfiles sont reconstruits sans recherche d’alternative, scannés par Trivy, démarrés et sondés localement. Toute nouvelle alerte ou dérive ramène au parcours complet. La configuration hébergeur, l’identité de l’image active, le contrôle HTTPS et la preuve Node finale sont revérifiés : le runtime exige encore une lecture dans les conteneurs, le site statique n’atteste que Node de construction. Aucun déploiement n’est publié sur ce raccourci. Les détails indiquent explicitement quels scripts n’ont pas été réexécutés et leur date réelle.

Le premier passage avec cette politique doit établir une référence par le parcours complet ; un ancien historique ne suffit pas. Ce mécanisme réduit les mises à jour sans changement, sans garantir une durée fixe ni dispenser des contrôles de sécurité et de production.

## Applications sans Git

Dans **Services, configuration et détails**, fournir une archive ZIP des sources complètes, avec `package.json`, le verrouillage et le bon répertoire de construction. Limite initiale : **2 Mo compressés**, sans `node_modules`, `.git`, fichiers `.env` réels, clés privées ni identifiants npm. Le plafond évite les limites de corps des fonctions Vercel ; les gros projets nécessitent une autre source de stockage avant de pouvoir être pris en charge. Les archives chiffrées, chemins traversants, liens et fichiers spéciaux sont refusés ; l’extraction est plafonnée à 150 Mo.

Les sources sont chiffrées en base. Leur configuration les associe au déploiement alors actif ; une modification extérieure détectée impose un nouvel import afin de ne pas écraser du code récent avec une ancienne archive. Vigie ne peut pas prouver que l’archive initialement fournie correspond au code distant : c’est une condition de l’import.

Après validation, seuls les fichiers sources d’origine et les fichiers de versions autorisés sont reconditionnés. Les artefacts, caches et `node_modules` produits par les tests ne sont pas envoyés. Vercel reçoit les fichiers via son API ; Railway reçoit une archive via sa CLI officielle, sans créer de dépôt Git. Les sources actualisées sont conservées pour l’exécution suivante et peuvent être téléchargées. L’archive précédente et la candidate sont également conservées chiffrées dans `update_snapshots` pour récupération administrative. Une archive candidate conservée n’est pas à elle seule une preuve que son déploiement a réussi.

Après toute modification externe du code, réimporter les sources actuelles. Un exécutable, une image Docker ou des fichiers compilés seuls ne remplacent pas les sources.

## WordPress sur o2switch

Le parcours **agent local sans SSH** est désormais disponible dans les sources : la configuration dépose un agent privé et une tâche cron via cPanel. Il réutilise les contrôles de sécurité ci-dessous mais exécute WP-CLI localement sur l’hébergement. Les clés SSH ne sont pas nécessaires à ce nouveau parcours. Le déploiement et l’exécution sur la production sont bloqués tant que `VIGIE_WORDPRESS_AGENT_PRODUCTION_ENABLED` n’est pas explicitement activé. Voir [protocole, installation, récupération et validation](agent-wordpress-local.md). La description SSH ci-dessous reste celle du parcours antérieur, conservé pour les accès déjà configurés.

Avant la sauvegarde et toute modification de fichiers, WP-CLI produit un plan frais des versions installées et proposées. Vigie vérifie les prérequis PHP/WordPress et les dépendances d’extensions déclarées, puis consulte **WPScan** pour le cœur, les extensions ordinaires et les thèmes installés, y compris inactifs. Le secret `VIGIE_UPDATES_WPSCAN_TOKEN` doit être ajouté à l’environnement GitHub `vigie-maintenance` ; il ne doit jamais être envoyé au navigateur ou au serveur o2switch. Sans ce jeton, si le quota est épuisé ou si WPScan ne couvre pas un composant, le parcours s’arrête avant la sauvegarde/mutation. Les extensions privées et MU nécessitent une qualification dédiée ; le plan ne certifie pas leur compatibilité.

Les versions candidates sont analysées avant installation selon la même politique que Node, puis installées explicitement avec leur numéro de version, et non via un `update --all` susceptible de sélectionner une autre publication entre-temps. Les versions précédentes sont revérifiées avant les mutations. Après installation, les versions réelles doivent correspondre au plan et sont réanalysées. Une version déjà corrigée dans une branche maintenue n’est pas signalée à tort si WPScan fournit plusieurs plages de correctifs. Les prérequis déclarés ne prouvent pas la compatibilité fonctionnelle entre extensions : aucune copie WordPress de préproduction ni test de commande/paiement n’est créé automatiquement dans cette version.

Le connecteur d’inventaire existant n’obtient aucune nouvelle permission d’écriture. La configuration initiale demande une clé SSH privée dédiée, autorisée sur le compte o2switch, et la clé publique du serveur confirmée hors bande. La clé doit être utilisable sans saisie de phrase secrète sur l’exécuteur ; elle est chiffrée en base et jamais renvoyée au navigateur. L’hôte et le compte viennent exclusivement de la connexion o2switch rattachée. WP-CLI doit déjà être disponible sur ce compte ; Vigie ne télécharge ni n’installe de binaire distant automatiquement.

Avant les mises à jour : contrôle HTTPS, relevé frais par le connecteur d’inventaire WordPress, concordance entre PHP web et PHP utilisé par WP-CLI, vérification du domaine WordPress, chemin réel dans le bon compte, refus des liens symboliques/multisites/modifications désactivées et contrôle de la base. Si PHP CLI diffère de PHP web, aligner le binaire utilisé avant d’activer le parcours : une compatibilité vérifiée uniquement dans le terminal ne garantit pas celle du site. Une sauvegarde SQL et une archive des fichiers sont créées dans un répertoire privé hors racine web, sous `/home/COMPTE/.vigie-backups/ID_EXECUTION/ID_SITE/`. La liste de l’archive et les empreintes SHA-256 sont vérifiées avant toute mise à jour. Chaque installation a un emplacement distinct.

WP-CLI met ensuite à jour le cœur, son schéma, les extensions et les thèmes, avec un mode maintenance temporaire et une tentative de désactivation dans le gestionnaire de sortie. Vigie vérifie les fichiers du cœur, les mises à jour encore proposées et la réponse HTTPS. Une coupure forcée peut nécessiter de retirer manuellement un mode maintenance résiduel. Un composant payant sans licence ou sans flux accessible n’est jamais garanti à jour. Les modifications personnalisées dans une extension/un thème peuvent être écrasées par sa mise à jour : conserver ces personnalisations dans les mécanismes prévus par WordPress.

La restauration des fichiers et de la base reste **manuelle après vérification de la sauvegarde**, car elle peut écraser des commandes, formulaires ou contenus créés après la sauvegarde. Le mode maintenance ne garantit pas l’absence de toute écriture externe. Les sauvegardes ne sont pas purgées automatiquement dans cette première version : surveiller le quota et définir une rétention adaptée. PHP, les bases hébergées et les images externes ne font pas partie de ce bouton.

## Activation administrateur

1. Appliquer `npm run db:migrate` contre la base cible après sauvegarde. La migration `004-updates.sql` n’efface aucune donnée historique.
2. Publier `.github/workflows/vigie-updates.yml` sur `main` du dépôt central `TheooLeroux/Vigie`.
3. Dans l’environnement GitHub existant `vigie-maintenance`, autorisé uniquement sur `main`, ajouter `VIGIE_UPDATES_DATABASE_URL` et `VIGIE_UPDATES_ENCRYPTION_KEY`. Ils correspondent à la base et à la clé de chiffrement utilisées par Vigie. Cet exécuteur central est de confiance : il doit être protégé comme le serveur Vigie. Aucun de ces secrets n’est transmis aux conteneurs qui testent les projets.
4. Cet environnement conserve les secrets dédiés `VIGIE_MAINTENANCE_GITHUB_TOKENS` et `VIGIE_MAINTENANCE_GITHUB_TOKEN_JANSSEN76140`, et la variable `VIGIE_MAINTENANCE_REPOSITORIES`. Ne jamais les remplacer par un jeton personnel global. Les accès aux dépôts cibles exigent Contents lecture/écriture ; le dépôt central exige aussi Actions lecture/écriture pour lancer et vérifier l’exécuteur. Aucune permission Checks/Commit statuses n’est nécessaire au nouveau parcours.
5. Côté Vigie, définir `VIGIE_UPDATES_RUNNER_REPOSITORY=TheooLeroux/Vigie`, `VIGIE_UPDATES_RUNNER_REF=main`, `VIGIE_UPDATES_REPOSITORIES` (liste explicite des dépôts autorisés), et les jetons dédiés par propriétaire. Les anciennes variables `VIGIE_MAINTENANCE_*` de jetons et périmètre sont acceptées en repli pour préserver les accès déjà créés. Une variable nouvelle non vide prend priorité ; ne pas définir `{}` si l’on veut utiliser l’ancien dictionnaire de jetons.
6. Les connexions Vercel/Railway doivent permettre les lectures de déploiements et, pour les projets sans Git, les écritures de déploiement. La sonde de runtime Railway exige un jeton API de workspace administrateur permettant de créer/révoquer la clé SSH temporaire ; un jeton de projet ne suffit pas ([documentation SSH Railway](https://docs.railway.com/cli/ssh)). Ne pas élargir les droits sans validation de l’administrateur. Un refus API n’est jamais assimilé à une réussite.
7. Configurer les sources sans Git et les accès SSH des WordPress concernés. Tester un projet pilote non critique, puis définir `VIGIE_UPDATES_ENABLED=1`. Le module reste désactivé tant que cette activation n’est pas explicite.

L’exécuteur peut aussi être lancé sur un Linux de confiance doté de Node 24, Docker, Python 3, OpenSSH et Railway CLI 5.71.0 : `node --import tsx scripts/update-worker.ts IDENTIFIANT`. Il utilise la même file durable et ne prend en charge qu’un job encore en attente. Le frontend et les routes Vercel n’exécutent jamais une construction longue après avoir répondu à une requête.

## Échecs et récupération

Pour un site protégé, le contrôle HTTPS doit viser le chemin de santé public déclaré chez l’hébergeur, pas une page qui exige une session. La documentation NesAppli utilise `/healthz` ; sa racine reste protégée et une réponse 401 ne doit jamais être acceptée comme un contrôle de santé réussi. Après changement du chemin chez Railway, synchroniser son inventaire dans Vigie avant de lancer une nouvelle mise à jour.

Un échec avant publication libère les verrous. Après une publication commencée, un résultat partiel ou un délai dépassé, le suivi reste **À vérifier** et conserve ses références. Ne pas relancer aveuglément : vérifier le commit, le déploiement et le site. Après 30 minutes sans progression, **Clôturer après vérification manuelle** exige une confirmation et vérifie d’abord que l’exécuteur GitHub est réellement terminé ; cette action ne restaure rien.

Un rollback d’hébergement ne remet pas automatiquement le dépôt à son ancien commit et ne restaure pas une base. Pour Git, rétablir explicitement les fichiers concernés dans un nouveau commit si nécessaire. Pour une source ZIP, récupérer l’archive précédente chiffrée avec un outil administratif autorisé, puis la réimporter. Pour WordPress, vérifier les sauvegardes et coordonner la restauration avec les éventuelles nouvelles écritures. En cas de doute, conserver le verrou et intervenir manuellement.

## Périmètre initial et qualification

- Applications Node standard npm, pnpm et Yarn ; plusieurs sous-répertoires indépendants d’un dépôt sont regroupés. Un Dockerfile situé dans un service indépendant ne bloque pas les autres. Les Dockerfiles Node standard sont admissibles après construction et contrôle du serveur ; les bases privées/non-Node, images à digest, frontends personnalisés, montages de build, chemins Dockerfile Railway personnalisés et instructions nécessitant une configuration spéciale restent refusés. Les workspaces, configurations Mise/Railpack personnalisées, commandes de construction Vercel personnalisées et versions Node forcées par une variable Railway différente demandent également une adaptation dédiée.
- Dépendances privées nécessitant des identifiants à l’installation : hors du parcours initial. Aucun secret de production n’est injecté pour faire passer artificiellement un build.
- Contrôle HTTP 200, activation du déploiement et scripts disponibles ne remplacent pas des tests métier, visuels, de paiement ou d’authentification de l’application mise à jour.
- Les tests locaux simulent les écritures des API distantes. `VIGIE_TEST_DOCKER=1 npm test` ajoute les installations et validations réelles npm, pnpm, Yarn Classic et Yarn moderne, ainsi que des scripts en échec ou altérant les sources. `VIGIE_TEST_WORDPRESS=1 npm test` ajoute un WordPress et une base MariaDB jetables : mise à jour réelle du cœur, des extensions et des thèmes, contrôle HTTP et restauration de la sauvegarde dans une seconde installation et une seconde base isolées. Ces tests demandent Docker et un accès réseau aux images et catalogues publics ; ils n’utilisent pas de secrets de production. Ils sont également demandés dans la CI.
- `VIGIE_UPDATES_TEST_DATABASE_URL` active le test PostgreSQL de migration et de concurrence dans un schéma jetable ; seules les adresses de boucle locale sont acceptées. Un pilote distant reste nécessaire avant de qualifier la publication, le déploiement et la restauration chez chaque type d’hébergeur. Un contrôle des API en lecture seule ne remplace pas ce pilote.
