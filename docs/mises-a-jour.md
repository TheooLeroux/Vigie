# Mises à jour depuis une fiche projet

## Parcours utilisateur

Un bouton **Tout mettre à jour** lance les services admissibles de la fiche. La progression et le résultat restent sur cette fiche ; les sources, les erreurs détaillées, les sauvegardes et les références de récupération sont repliées. Un double clic réutilise le même traitement. Les services hors périmètre restent identifiés dans les détails et leur nombre est affiché : le bouton ne prétend pas les mettre à jour.

Il n’y a ni PR à approuver, ni fusion manuelle. Les montées majeures des dépendances directes sont incluses lorsqu’elles sont compatibles. Node cible la dernière LTS encore maintenue, pas une version « Current » non LTS. Vigie recherche un ensemble de versions stables en tenant compte des moteurs Node et des dépendances homologues (`peerDependencies`) des versions candidates, pas seulement des versions déjà installées. Un parseur qui exige TypeScript inférieur à 6.1 conduit ainsi à sélectionner le TypeScript stable admissible le plus récent, plutôt qu’à imposer TypeScript 7 ou à bloquer les autres paquets. Les préversions, versions dépréciées et versions supérieures au dist-tag `latest` sont exclues ; les versions ne sont pas ramenées sous le minimum déjà déclaré. Les versions retenues pour compatibilité sont expliquées dans les détails.

La recherche est déterministe et bornée ; lorsqu’il existe plusieurs ensembles incomparables, elle choisit un ensemble valide en privilégiant les versions récentes, sans prétendre à un optimum mathématique unique. Les paquets dépréciés ou références locales/privées particulières sont conservés avec un avertissement. Les dépendances transitives sont résolues par le gestionnaire ; npm et pnpm doivent accepter strictement les pairs, sans `--force` ni `--legacy-peer-deps`. La compatibilité des déclarations ne prouve pas la compatibilité du code : installation, typage, tests et construction restent obligatoires avant publication.

Si le compilateur identifie une rupture d’API dans un paquet direct nouvellement monté de majeure, Vigie peut retenir la dernière version compatible de sa branche actuelle et refaire toute la validation, tout en conservant les mises à jour indépendantes. Les options TypeScript supprimées ou dépréciées bloquant le compilateur sont également reconnues. Ce repli est limité à trois essais pour le groupe de services ; un échec métier sans cause identifiable n’est jamais ignoré. Avant chaque essai, Vigie vérifie que les scripts n’ont altéré ni le code ni les manifestes/verrous validés. Les journaux bruts ne sont pas renvoyés dans l’application.

Pour npm, le verrou est recalculé dans le répertoire temporaire à partir des manifestes exacts retenus, plutôt que de réutiliser un ancien arbre contradictoire. Ce n’est pas une suppression du verrou publié : un nouveau verrou complet, puis une installation `npm ci` stricte et les tests, sont obligatoires. Le verrou précédent reste dans l’ancien commit ou la sauvegarde des sources.

Le backend NesAppli dispose d’un profil de test reconnu par son manifeste et son schéma de configuration : ses tests reçoivent uniquement des valeurs factices explicites, avec Supabase et SMTP pointant sur le port fermé 9 de la boucle locale du conteneur. Aucun accès ni secret de production n’est utilisé ; les appels aux services doivent être simulés par les tests du projet. Ce profil n’est jamais publié dans les sources et ne change pas la configuration Railway. Si les tests ont besoin de vrais services ou d’une autre configuration, la validation échoue : leurs assertions ne sont ni ignorées ni désactivées.

## Applications avec GitHub

Le traitement lit la branche de production et les répertoires effectivement rattachés au projet. Les services d’un même dépôt sont regroupés pour ne publier qu’un commit. Le dépôt entier est verrouillé, y compris s’il est partagé entre plusieurs fiches. Une publication sur une branche reliée à plusieurs hébergements peut naturellement déclencher leurs déploiements automatiques : les filtres de construction doivent être configurés chez les hébergeurs.

Les sources du dernier commit sont extraites dans un répertoire temporaire. Les manifestes et fichiers de version de Node sont actualisés, puis le gestionnaire résout un nouveau verrouillage. L’installation figée, le typage, les tests et la construction déclarés sont exécutés dans des conteneurs Docker limités, non privilégiés, sans les jetons GitHub/hébergeurs, la clé de chiffrement ni l’URL de base Vigie. Au moins un script `test` ou `build` est nécessaire. Les secrets de production ne sont pas fournis aux tests.

Une modification du code par les scripts, ou une modification des manifestes/verrous pendant les tests, annule la publication. La référence Git est avancée sans force, avec le commit testé comme parent : une modification concurrente n’est jamais écrasée. Les règles de protection GitHub ne sont pas contournées. Si la branche exige une PR, l’exécution directe ne peut pas publier sur cette branche.

Les Dockerfiles Node standard placés à la racine effective du service sont pris en charge, y compris les images multi-étapes comme celle de la documentation NesAppli : toutes les bases officielles `node:VERSION-VARIANTE` sont actualisées en préservant leur variante, ainsi que les paquets explicitement installés par une instruction npm simple. Un paquet runtime également présent dans le manifeste reçoit la même version compatible. Les instructions ne sont pas réécrites. Avant publication Git, les modifications du Dockerfile sont comparées au fichier du commit source : seules les versions peuvent changer.

L’image est reconstruite à partir des seuls fichiers sources et verrous autorisés, sans artefacts des tests ni secrets du worker. Elle doit démarrer sous le Node demandé et répondre à un contrôle HTTP local dans un conteneur sans réseau externe, à capacités supprimées et racine en lecture seule. Pour la documentation NesAppli protégée par SSO, seules des valeurs de configuration factices sont utilisées ; `/healthz` doit répondre et la racine sans session doit rester refusée. Cela ne remplace pas un test du SSO réel. Le Dockerfile historique de NesAppli installe son paquet runtime avec une version directe explicite mais sans verrouillage transitif dédié ; ce comportement n’est pas transformé silencieusement en un autre mode de construction.

Vigie attend le déploiement automatique du commit exact chez Vercel/Railway, son activation en production, puis un contrôle HTTPS public. Un ancien déploiement prêt n’est pas une preuve de réussite. Les déploiements automatiques Git doivent donc être activés. Les anciennes références de commit et de déploiement restent enregistrées ; aucune base applicative n’est restaurée automatiquement.

## Applications sans Git

Dans **Services, configuration et détails**, fournir une archive ZIP des sources complètes, avec `package.json`, le verrouillage et le bon répertoire de construction. Limite initiale : **2 Mo compressés**, sans `node_modules`, `.git`, fichiers `.env` réels, clés privées ni identifiants npm. Le plafond évite les limites de corps des fonctions Vercel ; les gros projets nécessitent une autre source de stockage avant de pouvoir être pris en charge. Les archives chiffrées, chemins traversants, liens et fichiers spéciaux sont refusés ; l’extraction est plafonnée à 150 Mo.

Les sources sont chiffrées en base. Leur configuration les associe au déploiement alors actif ; une modification extérieure détectée impose un nouvel import afin de ne pas écraser du code récent avec une ancienne archive. Vigie ne peut pas prouver que l’archive initialement fournie correspond au code distant : c’est une condition de l’import.

Après validation, seuls les fichiers sources d’origine et les fichiers de versions autorisés sont reconditionnés. Les artefacts, caches et `node_modules` produits par les tests ne sont pas envoyés. Vercel reçoit les fichiers via son API ; Railway reçoit une archive via sa CLI officielle, sans créer de dépôt Git. Les sources actualisées sont conservées pour l’exécution suivante et peuvent être téléchargées. L’archive précédente et la candidate sont également conservées chiffrées dans `update_snapshots` pour récupération administrative. Une archive candidate conservée n’est pas à elle seule une preuve que son déploiement a réussi.

Après toute modification externe du code, réimporter les sources actuelles. Un exécutable, une image Docker ou des fichiers compilés seuls ne remplacent pas les sources.

## WordPress sur o2switch

Le connecteur d’inventaire existant n’obtient aucune nouvelle permission d’écriture. La configuration initiale demande une clé SSH privée dédiée, autorisée sur le compte o2switch, et la clé publique du serveur confirmée hors bande. La clé doit être utilisable sans saisie de phrase secrète sur l’exécuteur ; elle est chiffrée en base et jamais renvoyée au navigateur. L’hôte et le compte viennent exclusivement de la connexion o2switch rattachée. WP-CLI doit déjà être disponible sur ce compte ; Vigie ne télécharge ni n’installe de binaire distant automatiquement.

Avant les mises à jour : contrôle HTTPS, relevé frais par le connecteur d’inventaire WordPress, concordance entre PHP web et PHP utilisé par WP-CLI, vérification du domaine WordPress, chemin réel dans le bon compte, refus des liens symboliques/multisites/modifications désactivées et contrôle de la base. Si PHP CLI diffère de PHP web, aligner le binaire utilisé avant d’activer le parcours : une compatibilité vérifiée uniquement dans le terminal ne garantit pas celle du site. Une sauvegarde SQL et une archive des fichiers sont créées dans un répertoire privé hors racine web, sous `/home/COMPTE/.vigie-backups/ID_EXECUTION/ID_SITE/`. La liste de l’archive et les empreintes SHA-256 sont vérifiées avant toute mise à jour. Chaque installation a un emplacement distinct.

WP-CLI met ensuite à jour le cœur, son schéma, les extensions et les thèmes, avec un mode maintenance temporaire et une tentative de désactivation dans le gestionnaire de sortie. Vigie vérifie les fichiers du cœur, les mises à jour encore proposées et la réponse HTTPS. Une coupure forcée peut nécessiter de retirer manuellement un mode maintenance résiduel. Un composant payant sans licence ou sans flux accessible n’est jamais garanti à jour. Les modifications personnalisées dans une extension/un thème peuvent être écrasées par sa mise à jour : conserver ces personnalisations dans les mécanismes prévus par WordPress.

La restauration des fichiers et de la base reste **manuelle après vérification de la sauvegarde**, car elle peut écraser des commandes, formulaires ou contenus créés après la sauvegarde. Le mode maintenance ne garantit pas l’absence de toute écriture externe. Les sauvegardes ne sont pas purgées automatiquement dans cette première version : surveiller le quota et définir une rétention adaptée. PHP, les bases hébergées et les images externes ne font pas partie de ce bouton.

## Activation administrateur

1. Appliquer `npm run db:migrate` contre la base cible après sauvegarde. La migration `004-updates.sql` n’efface aucune donnée historique.
2. Publier `.github/workflows/vigie-updates.yml` sur `main` du dépôt central `TheooLeroux/Vigie`.
3. Dans l’environnement GitHub existant `vigie-maintenance`, autorisé uniquement sur `main`, ajouter `VIGIE_UPDATES_DATABASE_URL` et `VIGIE_UPDATES_ENCRYPTION_KEY`. Ils correspondent à la base et à la clé de chiffrement utilisées par Vigie. Cet exécuteur central est de confiance : il doit être protégé comme le serveur Vigie. Aucun de ces secrets n’est transmis aux conteneurs qui testent les projets.
4. Cet environnement conserve les secrets dédiés `VIGIE_MAINTENANCE_GITHUB_TOKENS` et `VIGIE_MAINTENANCE_GITHUB_TOKEN_JANSSEN76140`, et la variable `VIGIE_MAINTENANCE_REPOSITORIES`. Ne jamais les remplacer par un jeton personnel global. Les accès aux dépôts cibles exigent Contents lecture/écriture ; le dépôt central exige aussi Actions lecture/écriture pour lancer et vérifier l’exécuteur. Aucune permission Checks/Commit statuses n’est nécessaire au nouveau parcours.
5. Côté Vigie, définir `VIGIE_UPDATES_RUNNER_REPOSITORY=TheooLeroux/Vigie`, `VIGIE_UPDATES_RUNNER_REF=main`, `VIGIE_UPDATES_REPOSITORIES` (liste explicite des dépôts autorisés), et les jetons dédiés par propriétaire. Les anciennes variables `VIGIE_MAINTENANCE_*` de jetons et périmètre sont acceptées en repli pour préserver les accès déjà créés. Une variable nouvelle non vide prend priorité ; ne pas définir `{}` si l’on veut utiliser l’ancien dictionnaire de jetons.
6. Les connexions Vercel/Railway doivent permettre les lectures de déploiements et, pour les projets sans Git, les écritures de déploiement. Ne pas élargir leurs droits sans validation de l’administrateur. Les jetons Railway existants peuvent devoir être renouvelés côté hébergeur : un refus API n’est jamais assimilé à une réussite.
7. Configurer les sources sans Git et les accès SSH des WordPress concernés. Tester un projet pilote non critique, puis définir `VIGIE_UPDATES_ENABLED=1`. Le module reste désactivé tant que cette activation n’est pas explicite.

L’exécuteur peut aussi être lancé sur un Linux de confiance doté de Node 24, Docker, Python 3, OpenSSH et Railway CLI 5.71.0 : `node --import tsx scripts/update-worker.ts IDENTIFIANT`. Il utilise la même file durable et ne prend en charge qu’un job encore en attente. Le frontend et les routes Vercel n’exécutent jamais une construction longue après avoir répondu à une requête.

## Échecs et récupération

Un échec avant publication libère les verrous. Après une publication commencée, un résultat partiel ou un délai dépassé, le suivi reste **À vérifier** et conserve ses références. Ne pas relancer aveuglément : vérifier le commit, le déploiement et le site. Après 30 minutes sans progression, **Clôturer après vérification manuelle** exige une confirmation et vérifie d’abord que l’exécuteur GitHub est réellement terminé ; cette action ne restaure rien.

Un rollback d’hébergement ne remet pas automatiquement le dépôt à son ancien commit et ne restaure pas une base. Pour Git, rétablir explicitement les fichiers concernés dans un nouveau commit si nécessaire. Pour une source ZIP, récupérer l’archive précédente chiffrée avec un outil administratif autorisé, puis la réimporter. Pour WordPress, vérifier les sauvegardes et coordonner la restauration avec les éventuelles nouvelles écritures. En cas de doute, conserver le verrou et intervenir manuellement.

## Périmètre initial et qualification

- Applications Node standard npm, pnpm et Yarn ; plusieurs sous-répertoires indépendants d’un dépôt sont regroupés. Un Dockerfile situé dans un service indépendant ne bloque pas les autres. Les Dockerfiles Node standard sont admissibles après construction et contrôle du serveur ; les bases privées/non-Node, images à digest, frontends personnalisés, montages de build, chemins Dockerfile Railway personnalisés et instructions nécessitant une configuration spéciale restent refusés. Les workspaces, configurations Mise/Railpack personnalisées, commandes de construction Vercel personnalisées et versions Node forcées par une variable Railway différente demandent également une adaptation dédiée.
- Dépendances privées nécessitant des identifiants à l’installation : hors du parcours initial. Aucun secret de production n’est injecté pour faire passer artificiellement un build.
- Contrôle HTTP 200, activation du déploiement et scripts disponibles ne remplacent pas des tests métier, visuels, de paiement ou d’authentification de l’application mise à jour.
- Les tests locaux simulent les écritures des API distantes. `VIGIE_TEST_DOCKER=1 npm test` ajoute les installations et validations réelles npm, pnpm, Yarn Classic et Yarn moderne, ainsi que des scripts en échec ou altérant les sources. `VIGIE_TEST_WORDPRESS=1 npm test` ajoute un WordPress et une base MariaDB jetables : mise à jour réelle du cœur, des extensions et des thèmes, contrôle HTTP et restauration de la sauvegarde dans une seconde installation et une seconde base isolées. Ces tests demandent Docker et un accès réseau aux images et catalogues publics ; ils n’utilisent pas de secrets de production. Ils sont également demandés dans la CI.
- `VIGIE_UPDATES_TEST_DATABASE_URL` active le test PostgreSQL de migration et de concurrence dans un schéma jetable ; seules les adresses de boucle locale sont acceptées. Un pilote distant reste nécessaire avant de qualifier la publication, le déploiement et la restauration chez chaque type d’hébergeur. Un contrôle des API en lecture seule ne remplace pas ce pilote.
