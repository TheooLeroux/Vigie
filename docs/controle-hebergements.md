# Maintenir les contrôles des hébergements

Le workflow `vigie-wordpress-agents.yml` programme un contrôle toutes les cinq minutes, sans ouvrir Vigie. Il utilise les accès chiffrés existants et l’environnement GitHub `vigie-maintenance`. Le même workflow passe après toute publication sur `main`, après un événement GitHub `deployment_status` réussi sur cette branche et peut être lancé manuellement. La fréquence est une cadence demandée : les délais GitHub Actions, une panne réseau ou une installation longue peuvent retarder le passage. Ce dispositif ne garantit pas une disponibilité sans interruption.

## Analyses autonomes des failles et des mises à jour

### Bilan quotidien des versions stables

Le workflow `vigie-daily-assessments.yml` programme chaque jour à 03 h 17 UTC (04 h 17 en hiver et 05 h 17 en été à Paris) un bilan préalable des projets actifs. Il peut aussi être lancé manuellement. GitHub Actions peut retarder son démarrage. Le plan crée au plus un bilan par projet et par jour UTC ; deux projets sont traités simultanément. Les projets archivés sont exclus. Les accès et l’environnement `vigie-maintenance` existants sont réutilisés, sans nouveau secret ni migration.

Le workflow réutilise `vigie-updates.yml` avec une finalité `assessment` vérifiée avant l’exécution. Le moteur suit les mêmes étapes de préparation, puis s’arrête avant l’installation :

- Node : récupération des sources, recherche de versions stables, résolution des dépendances et replis de compatibilité, scans de sécurité, constructions et scripts de tests disponibles en conteneurs isolés. Les fichiers candidats ne sont ni committés, ni déployés, ni conservés comme sources installées. La validation lourde n’est pas remplacée par un ancien reçu dans ce bilan.
- WordPress : inspection du plan par l’agent existant ou SSH, vérification des prérequis et scans des versions candidates. Aucune demande de sauvegarde, installation ou restauration n’est envoyée. La recette métier de la candidate reste à faire sur une copie ; une comparaison de prérequis n’est pas présentée comme un test intégral du site.
- Image Tailscale qualifiée : contrôle de la configuration et du réseau actuel, comparaison de l’empreinte stable, scan de l’image et lecture isolée de sa version. Aucun remplacement, déploiement, snapshot ni renouvellement d’autorisation n’est demandé. La reconnexion de la candidate sera contrôlée lors d’une installation explicite.

Les bilans et les installations restent séparés dans l’API et l’interface. Les mêmes verrous de sources empêchent leur exécution simultanée ; un bilan interrompu sans battement depuis deux heures est libéré au prochain plan quotidien. Les blocs manuels ou non qualifiés restent signalés, sans succès inventé. Un échec d’un groupe ne supprime pas le résultat des autres.

Une proposition est liée au déploiement, aux sources et à sa date. Après 24 heures, un changement de déploiement ou une maintenance plus récente, elle redevient à actualiser. Pour les blocs validés, le compteur utilise les changements retenus par le moteur et retire les simples comparaisons de catalogue ; les versions non validées restent identifiées comme telles. Les alertes de sécurité et interventions manuelles restent affichées séparément.

Après une installation réussie et une observation confirmant le déploiement contrôlé, un bilan après maintenance remplace immédiatement les estimations de catalogue pour les blocs couverts. Il ne déclare pas les autres blocs à jour et n’empêche pas le prochain bilan quotidien. Une observation manquante ou différente ne produit aucun faux résultat actuel. Le bouton d’installation relance toujours ses propres contrôles ; un bilan quotidien ne lui donne aucune dispense de validation.

### Contrôle horaire des versions installées

Après la synchronisation de chaque hébergeur, le worker `scripts/automatic-control-worker.ts` parcourt les projets actifs de son périmètre. Il analyse chaque service au premier passage, lorsque son déploiement ou ses versions WordPress changent, puis à l’expiration d’une heure. Les déploiements des projets surveillés sont détectés par les lectures périodiques des API Vercel/Railway ; aucun webhook n’est installé dans ces projets. Ils déclenchent leur analyse au passage qui les découvre. Un déploiement intermédiaire remplacé entre deux lectures ne peut pas être garanti comme analysé.

WordPress utilise un inventaire existant renouvelé par le contrôle des agents et un nouveau relevé WPVulnerability, y compris lorsque les versions n’ont pas changé. Le cœur, les extensions ordinaires et les thèmes publics identifiables sont analysés, y compris inactifs ; les composants privés, thèmes enfants et MU-plugins gardent une couverture manuelle explicite. Les informations de versions disponibles sont relevées par le connecteur WordPress. Les caches des catalogues WordPress.org, PHP.net, Node et npm sont limités à une heure. Voir [la maintenance des composants conservés](o2switch-maintenance.md).

Un inventaire signé du connecteur en mode de secours permet également d’analyser les versions du cœur et des extensions lues dans leurs fichiers. Le rapport indique cette réserve : il ne confirme ni le bon chargement de WordPress ni la disponibilité de la maintenance. Les barrières de mise à jour, qui exigent un chargement complet et les preuves de l’agent, restent applicables.

Pour Node sur Vercel/Railway, la sonde lit uniquement le manifeste et le verrou du commit identifié par l’hébergeur, dans le répertoire du service, depuis un dépôt GitHub déjà autorisé. Elle ne se rabat jamais sur la tête de branche. OSV analyse les dépendances résolues, puis les versions stables disponibles des dépendances directes sont comparées au registre npm. Aucun script du projet n’est exécuté et aucun paquet du projet n’est installé. L’image système, les secrets et le code applicatif ne sont pas analysés par cette sonde. Un verrou absent, des sources non GitHub, des sources trop volumineuses, plusieurs commits simultanément actifs ou un commit déployé inconnu produisent une erreur explicite ; aucune absence de faille n’en est déduite.

Les résultats et les verrous utilisent des clés distinctes du catalogue durable `wordpress_catalog` existant : aucune migration ni nouveau secret n’est nécessaire. Un échec conserve les dernières preuves datées, retire leur validité et prévoit une nouvelle tentative au passage suivant après cinq minutes. Les rapports d’un ancien déploiement ne valident jamais le nouveau. Un verrou de dix minutes protège chaque service ; après arrêt brutal du worker, il devient récupérable. Les projets archivés et les installations ignorées ne sont pas analysés. Un échec n’empêche pas de traiter les autres projets et hébergeurs.

L’API des fiches lit les rapports enregistrés et le cache WordPress sans déclencher de scan distant. La vue d’ensemble affiche les alertes, les versions disponibles, les dates, les réserves et les erreurs de contrôle. Les alertes connues du même déploiement restent visibles pendant une panne ; une ancienne absence d’alerte ne vaut pas confirmation actuelle.

Pour activer ce comportement en production, publier ces fichiers et le workflow sur la branche principale. Les jobs Node réutilisent `VIGIE_MAINTENANCE_GITHUB_TOKENS`, le jeton séparé Janssen si présent et la variable `VIGIE_MAINTENANCE_REPOSITORIES` du parcours de maintenance. Le worker n’utilise pas le drapeau d’activation des mises à jour : la surveillance fonctionne indépendamment du droit de publier des correctifs. Les scanners ne sont téléchargés que si un contrôle Node est dû.

La surveillance des dépendances utilise les droits de lecture GitHub déjà accordés au jeton pour le dépôt identifié par l’hébergeur. La liste des dépôts autorisés à publier une mise à jour ne bloque pas ces lectures et reste exigée pour toute écriture. Une image externe (par exemple PostgreSQL) suit le parcours Trivy décrit ci-dessous ; un service sans source ou image vérifiable garde un périmètre manquant explicite.

### Compteur et couverture de sécurité

La colonne **Failles connues** compte les vulnérabilités applicables aux composants analysés. Les alias CVE/GHSA sont regroupés, y compris lorsqu’un avis relie deux groupes d’identifiants. Le décompte est distinct pour chaque service, composant et version. Les fins de support, publications générales de sécurité, signaux de distribution suspecte et avis dont l’applicabilité n’est pas établie sont affichés séparément. Un résultat sur un verrou partagé entre applications reste à confirmer, même si le scan a réussi.

Chaque service affiche le périmètre analysé, les réserves, la date du dernier rapport et l’action nécessaire pour compléter la couverture. Le dénominateur comprend aussi les ressources observées qui n’ont pas encore de cible de maintenance. Un projet sans scan exploitable n’affiche pas un faux zéro. « Périmètre couvert » signifie que les périmètres déclarés de tous les services sont analysés avec des rapports frais et liés à leur état actuel ; cela ne certifie pas le code métier, les secrets ni toutes les couches de l’hébergement. Une erreur de catalogue des mises à jour ne rend pas à elle seule le scan de vulnérabilités incomplet.

Les nouveaux rapports enregistrent une couverture structurée dans le catalogue durable existant, sans migration ni secret supplémentaire. Les anciens rapports restent lisibles ; les réserves WordPress et les verrous partagés restent explicites jusqu’au renouvellement. Les dépendances npm attestées exclusivement de développement sont identifiées comme « Développement / construction » ; les autres formats restent « Usage à qualifier » tant qu’aucune preuve plus précise n’est disponible.

### Dépendances hors Node et images publiques

La surveillance en lecture seule reconnaît également les sources PHP (`composer.lock`), Python (`uv.lock`, `poetry.lock`, `Pipfile.lock`, `pdm.lock`, `pylock.toml`), Go (`go.mod`), Rust (`Cargo.lock`), Ruby (`Gemfile.lock`, `gems.locked`) et Bun (`bun.lock`). Elle lit uniquement les fichiers résolus du commit identifié par l’hébergeur, vérifie leur analyse effective par OSV et conserve les limitations lorsque plusieurs environnements ou un workspace sont présents. Aucun script ni gestionnaire de paquets du projet n’est lancé. Ces parcours n’activent pas la maintenance de ces technologies. Une source mixte, un format absent ou des versions non identifiables restent à qualifier.

Les services Railway utilisant une image externe publique peuvent être analysés par Trivy lorsque les déploiements actifs exposent une même empreinte SHA-256. Le scan porte sur cette empreinte, jamais sur le dernier contenu d’un tag. Les registres pris en charge sont Docker Hub, GHCR, Quay, GCR, Microsoft Container Registry et `registry.k8s.io`, en accès anonyme. Trivy inspecte les couches à distance, avec un plafond de 2 Go et un délai de cinq minutes, sans démarrer de conteneur ni recevoir les secrets hébergeurs. Une image privée, une empreinte absente ou contradictoire, plusieurs images actives ou un rapport système inexploitable laissent la couverture non confirmée. Les volumes, la configuration et le code métier restent hors du scan. Une distribution en fin de support apparaît dans les autres alertes.

Validation locale du 29 octobre 2026 : tests de comptage, couverture, fraîcheur, accès et isolation ; essais réels OSV 2.7.0 sur des fixtures publiques Composer, Go, Cargo, uv, Ruby et Bun ; essai Trivy 0.76.1 sur une image Alpine publique liée à son empreinte. Les fixtures vulnérables ont produit des alertes. Ces essais ne sont pas des analyses du parc client. La publication du code et du workflow existant est nécessaire pour activer les nouveaux parcours sur l’exécuteur.

Lorsqu’un service utilise un verrou partagé dans un répertoire parent du dépôt, la sonde recherche les parents au même commit. Elle exige que le verrou pnpm/npm référence ce workspace et ses contraintes de dépendances, ou que le manifeste Yarn le déclare. L’analyse couvre alors le verrou partagé : les alertes sont signalées avec une réserve sur leur applicabilité au seul service, et les mises à jour de ses dépendances ne sont pas déduites des versions des autres workspaces.

## o2switch et WordPress

### Sources sans dépôt et sites statiques

Le contrôle Vercel utilise aussi les fichiers du déploiement de production lorsque GitHub n’est pas disponible ou que le parcours Git ne fournit pas de rapport. Il vérifie le projet, l’identifiant du déploiement et l’empreinte SHA-1 de chaque fichier. Les sources originales sont distinguées des sorties compilées. Les fichiers de dépendances sont analysés par OSV ; les pages HTML et scripts sont inspectés pour identifier les bibliothèques CDN à version exacte (jsDelivr, unpkg, esm.sh, Skypack, cdnjs avec correspondances connues, jQuery). Seuls les noms et versions de ces composants sont transmis au catalogue OSV, jamais le code des pages. Les sources statiques GitHub disposent du même parcours, lié au commit et aux empreintes Git.

Les installations o2switch hors WordPress peuvent fournir leurs fichiers HTML, JavaScript, CSS et leurs manifests/verrous par des lectures cPanel ciblées sous la racine rattachée. Aucun fichier du site n’est modifié et aucun code récupéré n’est exécuté. Les secrets, liens symboliques et répertoires de dépendances générés sont exclus. Les erreurs de lecture, répertoires non parcourus et limites de volume/durée rendent la couverture partielle. Une source sans accès exploitable reste signalée avec sa cause ; aucune autorisation supplémentaire n’est inventée.

La fiche affiche l’origine de la lecture, le déploiement Vercel, la liste des fichiers consultés et les composants identifiés. Un verrou npm attestant réellement l’absence de dépendances peut produire zéro pour ce périmètre ; une version non résolue, un échec de catalogue ou un verrou illisible ne constitue pas une preuve de zéro. Les pages statiques restent en couverture partielle : le code personnalisé, les bibliothèques incorporées et les chargements construits dynamiquement ne sont pas audités exhaustivement. Les polices Google sont distinguées des bibliothèques logicielles. Ce parcours n’active pas la maintenance automatique des sites jusque-là non qualifiés.

Chaque passage recherche les installations sur les comptes configurés, y compris celles précédemment marquées absentes. Une remise en ligne au même emplacement conserve ainsi le rattachement et les clés. Un répertoire ou un domaine différent doit d’abord être découvert et rattaché correctement. La recherche ne crée aucune fiche de projet.

Le contrôle des agents vérifie aussi un inventaire web de moins de cinq minutes. Si le connecteur d’inventaire ne répond plus, la collecte contrôle son fichier par cPanel. Un fichier absent et son dossier MU-plugins sont recréés avec la clé existante. Une ancienne version dont l’empreinte est connue peut être remplacée. Un fichier inconnu, modifié, un lien symbolique ou un emplacement hors du compte reste refusé ; le dernier inventaire est conservé avec son erreur. Les sites sans fiche active, ignorés ou absents ne reçoivent pas de connecteur automatique.

Un agent n’est sain que si son battement signé date de moins de trois minutes et son inspection WordPress signée de moins de dix minutes. La racine, le domaine, l’environnement et le PHP web doivent correspondre ; WordPress doit autoriser les modifications et ne pas être multisite. Le lanceur renouvelle cette inspection toutes les cinq minutes, même sans changement de sa configuration. Un cron qui tourne avec un WordPress devenu inutilisable ne suffit plus à confirmer le contrôle.

La réparation remet immédiatement l’agent en attente et retire son état prêt. Elle conserve la clé, les tâches, les résultats et les sauvegardes, puis vérifie le dépôt, le cron, le battement et WordPress avant de confirmer le retour du contrôle. Les erreurs persistantes utilisent la temporisation existante de cinq à soixante minutes. Une maintenance verrouillée garde la priorité. Les modifications distantes inconnues ne sont pas écrasées.

La dernière vérification réussie est enregistrée côté serveur. Après quinze minutes sans confirmation, la fiche indique que le contrôle a expiré et bloque une nouvelle mise à jour jusqu’au retour d’une preuve fraîche. Les installations partielles et les échecs restent visibles dans les détails de l’agent et l’activité.

Les sites o2switch autres que WordPress restent suivis par la découverte cPanel. Cette version n’y installe pas d’agent de maintenance.

## Vercel et Railway

Deux tâches indépendantes vérifient les connexions et relisent les projets, services et déploiements par les API des hébergeurs. Leur contrôle ne dépend pas d’un fichier dans les sources du site : un redéploiement retrouve son état au passage suivant, sans ajout de code au projet ni modification de son déploiement.

Une panne de connexion conserve le dernier relevé daté et son erreur. Un relevé de plus de quinze minutes expire également si le contrôle périodique ne passe plus. Elle empêche de proposer la cible comme disponible pour une mise à jour. Les autres comptes et l’autre hébergeur continuent d’être vérifiés. Les conflits de synchronisation et les limites temporaires sont différés au passage suivant. Un jeton révoqué, expiré ou insuffisant doit être remplacé dans Connexions : Vigie ne peut pas recréer une autorisation chez l’hébergeur sans accès valide.

## Exécution et validation

Le contrôle nécessite la publication du code et du workflow sur la branche principale, ainsi que les secrets déjà utilisés par l’installation des agents (`VIGIE_UPDATES_DATABASE_URL`, `VIGIE_UPDATES_ENCRYPTION_KEY`). Aucun nouveau secret ni migration n’est ajouté. Les contrôles web WordPress du worker passent par `VIGIE_WORDPRESS_CONTROL_URL`, configuré sur le serveur Vigie. La collecte web peut réparer uniquement le connecteur d’inventaire autorisé ; les opérations de maintenance restent réservées à l’agent privé.

Les tests simulent notamment la suppression du dossier MU-plugins après restauration, la conservation de la clé, le refus d’un fichier modifié, l’expiration des preuves, un PHP ou domaine différent et l’isolation des pannes entre comptes. Le test Docker du lanceur vérifie le renouvellement d’une inspection devenue fausse malgré une configuration inchangée.

Le contrôle et sa réparation ne lancent aucune mise à jour du contenu, sauvegarde ou restauration du site. Les erreurs sont visibles dans Vigie et les échecs du workflow ; aucune notification externe supplémentaire n’est créée.
