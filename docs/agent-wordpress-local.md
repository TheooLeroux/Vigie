# Agent WordPress local sans SSH

## Parcours et déploiement

L’agent complète le connecteur d’inventaire existant. Le connecteur reste en lecture seule ; la version 1.0.4 peut signaler passivement la présence d’un agent. Les autorisations de maintenance utilisent une autre clé, conservée chiffrée dans `update_sources` et dans un dossier privé de l’hébergement. La clé de l’observateur n’autorise aucune mutation.

Le rattachement d’un WordPress et les synchronisations o2switch demandent automatiquement son installation. Le workflow `vigie-wordpress-agents.yml` dépose les fichiers par cPanel, crée une tâche cron et attend un battement signé puis un contrôle signé du chargement WordPress par WP-CLI. Aucune clé SSH ni dépôt Git du site n’est nécessaire. La demande est chiffrée et conservée dans `update_sources` : la fiche affiche l’attente, l’installation, la réussite ou l’échec. Le bouton des détails permet de réessayer un échec sans ressaisir les accès.

Le workflow demande un passage toutes les cinq minutes pour rattraper les sites déjà rattachés et les déclenchements manqués. Les demandes ont un propriétaire temporaire, un identifiant et une temporisation de reprise ; deux workers ne provisionnent pas simultanément le même agent. La clé est enregistrée avant tout dépôt et conservée après une interruption. Seuls les WordPress retrouvés, non ignorés et rattachés à un projet actif sont éligibles. Les accès existants à la base et la clé de chiffrement de l’environnement GitHub `vigie-maintenance` suffisent à installer les agents.

Ce contrôle vérifie aussi le battement signé et une inspection WordPress signée récente des agents déjà installés. Un inventaire web frais vérifie le PHP et répare au besoin le connecteur disparu. Voir le [contrôle des hébergements](controle-hebergements.md) pour les seuils, la reprise et les limites de fréquence. Un agent absent ou arrêté revient automatiquement dans la file de provisionnement avec sa clé existante ; une maintenance en cours conserve la priorité. Un agent sain et à la version courante n’est pas redéployé. Les versions gérées antérieures sont mises à niveau automatiquement, avec vérification des empreintes et de la clé propriétaire ; les clés, tâches et sauvegardes sont conservées. Les fichiers inconnus restent protégés contre l’écrasement, y compris lors d’une réparation.

L’installation sur les sites de production est automatique ; elle ne lance aucune sauvegarde, mise à jour ou restauration WordPress. L’exécution des mises à jour de production reste conditionnée à `VIGIE_WORDPRESS_AGENT_PRODUCTION_ENABLED=1`, dans l’application et dans l’environnement GitHub `vigie-maintenance`, après validation du pilote. Le contrôle gratuit WPVulnerability est utilisé pour WordPress et les extensions, sans compte ni jeton. La fiche explique ces blocages distinctement de l’installation. Le déploiement sur une copie client chez o2switch reste une qualification différente du test Docker isolé.

Le dossier est `/home/COMPTE/.vigie-agent/EMPREINTE_RACINE/`, en 0700, hors des racines web cPanel. Il contient `agent.php`, `plan.php`, `config.json`, `jobs/`, `results/`, `backups/` et le battement. Le fichier de configuration contient les empreintes SHA-256 du code de l’agent et du générateur de plan. Un fichier inconnu ou altéré n’est jamais écrasé automatiquement. Les empreintes de versions gérées connues et les paramètres de propriété permettent une mise à niveau du paquet de l’agent. Les tentatives d’installation interrompues conservent leur clé pour permettre une reprise vérifiable.

La tâche cron appelle le PHP de la branche web (`/opt/alt/phpXX/usr/bin/php`) et l’agent une fois par minute. WP-CLI est utilisé **localement**, avec ce même PHP et sans connexion SSH. Son emplacement initial est `/usr/local/bin/wp` ; une différence réelle d’installation doit être diagnostiquée avant activation. Le battement puis une opération d’inspection doivent confirmer le même PHP exact que le relevé web, un WordPress chargeable et le domaine attendu. Une installation partielle ou un PHP différent ne marque pas la cible prête.

Le lanceur privé `bootstrap.php` prépare automatiquement Phar, nécessaire au binaire WP-CLI : si le PHP courant ne le charge pas, les processus CLI enfants lisent également le fichier privé `php.d/10-phar.ini`. Le paramètre `PHP_INI_SCAN_DIR` conserve les dossiers existants. La configuration PHP du site web reste inchangée. Une ancienne tâche cron de l’agent est remplacée par celle du lanceur, en conservant toutes les autres tâches du compte. L’inspection réelle reste obligatoire : une extension absente du serveur ou un WordPress cassé produit un échec visible et une nouvelle tentative, jamais une fausse réussite.

La qualification initiale vérifie `core is-installed`, le domaine, le PHP, le chargement WordPress et ses permissions de maintenance. Son résultat HMAC est enregistré dans `readiness.json`, renouvelé toutes les cinq minutes et lorsque la configuration de l’agent est redéposée. Elle ne construit pas de plan de mise à jour : un thème personnalisé sans version n’empêche pas d’installer l’agent. Le plan complet, les versions prises en charge, les prérequis et WPVulnerability sont toujours vérifiés séparément avant une mise à jour ; installer l’agent n’atteste pas que chaque composant peut être mis à jour automatiquement.

## Protocole et opérations

Vigie dépose dans `jobs/` des fichiers JSON enveloppés dans une signature HMAC-SHA256. Le canal est l’API cPanel authentifiée avec les accès existants ; aucun nouvel endpoint public d’écriture n’est exposé dans WordPress. Le nom du fichier, l’identifiant de demande, le traitement Vigie et la racine sont liés par la signature. L’agent refuse les ordres non signés, périmés, les autres racines et les opérations inconnues. Il n’accepte ni commande shell, ni script, ni chemin de sauvegarde fourni librement par une requête.

Les quatre opérations sont `inspect`, `backup`, `update` et `restore`. Les commandes locales sont construites par le code de l’agent avec des tableaux d’arguments, sans shell. La même combinaison traitement/opération a un identifiant stable : un double envoi récupère le même résultat. Une demande ayant commencé, échoué ou été interrompue n’est pas rejouée automatiquement. Un verrou de fichier empêche deux instances du cron de travailler simultanément sur l’installation. Une seule opération est traitée par passage.

Les résultats et battements sont signés dans l’autre sens. L’exécuteur vérifie la signature, les identifiants et la racine avant de les utiliser. Les journaux bruts PHP/WP-CLI ne quittent pas le compte ; les erreurs sont des codes bornés. Une absence de confirmation arrête le suivi sans réémettre une mutation.

`inspect` relève un plan frais et les réglages effectifs WordPress. Vigie conserve les contrôles existants : inventaire web récent, PHP identique, refus des multisites et des modifications désactivées, prérequis et WPVulnerability avant sauvegarde et mise à jour. Aucun secret de service de vulnérabilités n’est nécessaire.

Le paquet `core-plugins-free-v5` ajoute une qualification d’intégrité avant remplacement : extensions publiques personnalisées, distributions privées et cœur modifié restent conservés avec une intervention manuelle, sans bloquer les autres mises à jour admissibles. Les alertes portant sur ces versions conservées restent visibles. Les thèmes publics sont analysés mais toujours conservés. Le résultat distingue la fin de la maintenance automatique et les interventions restantes ; voir [la politique o2switch](o2switch-maintenance.md).

`backup` refuse les liens symboliques et fichiers spéciaux, vérifie une réserve de disque, active la maintenance et crée une archive des fichiers et un export SQL transactionnel. Une liste d’archive et des empreintes sont vérifiées ; un manifeste signé lie la copie à la racine et au traitement. La maintenance ne bloque pas toutes les écritures externes : les intégrations, commandes et moteurs de tables doivent être qualifiés pour chaque site avant de revendiquer une sauvegarde métier cohérente. Les sauvegardes sont conservées hors racine web, mais restent sur le même hébergement : une copie externe et une rétention restent à organiser.

`update` relit les versions installées, vérifie le manifeste de sauvegarde et applique les numéros de version explicitement validés, sans `update --all`. Le cœur, son schéma et les extensions utilisent WP-CLI local. Les thèmes restent inchangés, y compris les thèmes personnalisés sans version. PHP est uniquement relevé : le runtime web n’est jamais mis à jour par Vigie. Les prérequis sont comparés au PHP fourni par l’hébergeur, et les propositions incompatibles sont différées. Le cœur est contrôlé et le cache purgé. L’agent vérifie les versions réellement installées ; Vigie contrôle ensuite HTTPS et WPVulnerability. Les flux premium doivent fournir les versions demandées ; un flux non disponible reste un échec ou une réserve explicite. Les personnalisations et MU-plugins ne sont pas remplacés comme des extensions publiques.

## Récupération

La récupération ne dépend pas du chargement du WordPress en panne. L’agent CLI et les sauvegardes sont hors de son dossier. L’opération `restore` vérifie les empreintes, extrait l’ancienne archive dans un dossier privé, met les fichiers défaillants en quarantaine et rétablit les fichiers puis la base. La base est importée après restauration du code, afin qu’un cœur cassé n’empêche pas la réparation. Une erreur conserve les sauvegardes et la quarantaine ; une restauration incomplète peut laisser la maintenance active et demande une intervention.

La restauration complète est actuellement réservée aux préproductions avec `confirmDataLoss=true` explicite. Elle n’est jamais déclenchée automatiquement, et n’est pas proposée comme retour de production sans décision sur les commandes ou contenus reçus depuis la sauvegarde. Une requête de restauration refusée garde son résultat : une nouvelle décision utilise un nouvel identifiant de demande.

Les états `running` laissés par un arrêt forcé et les expirations de suivi exigent un diagnostic ; l’agent ne promet pas une reprise sûre d’une mutation partiellement effectuée. Les fichiers de tâches, les résultats, sauvegardes et quarantaines ne sont pas purgés automatiquement dans cette version. Surveiller le quota et prévoir leur archivage.

## Validation isolée

`VIGIE_TEST_WORDPRESS_AGENT=1 npx tsx --test tests/wordpress-agent.integration.test.ts` crée un WordPress et une base MariaDB jetables, en fait une copie avec une base distincte, installe l’agent uniquement sur cette copie et appelle le même client de tâches que Vigie. Le test exécute les mises à jour réelles, contrôle HTTP, vérifie que l’original est inchangé, casse volontairement le cœur de la copie et restaure fichiers et données sans SSH. Les signatures invalides, répétitions, refus PHP et confirmations de restauration sont aussi contrôlés. Les conteneurs et volumes créés par le test sont supprimés à la fin ; un rapport sans secret reste dans `.data/analysis/wordpress-local-agent-pilot.json`.

Ce test valide les mises à jour et la restauration sur un vrai WordPress isolé. Il ne prétend pas qualifier une copie d’un client, les extensions premium, la couverture complète des catalogues privés ou les paiements d’une boutique. L’installation réelle peut être qualifiée séparément, sans mettre à jour les sites : API cPanel, permissions privées, cron, battement signé et inspection locale.

## Contrôle gratuit et périmètre

WPVulnerability fournit une API publique sans jeton pour le cœur et les extensions ; les données sont réutilisables commercialement selon sa FAQ. Références : https://www.wpvulnerability.com/faq/ et https://docs.wpvulnerability.com/. Les réponses sont mises en cache pendant une heure pour limiter les appels entre sites. Une panne ou un rapport incomplet bloque les modifications. Les failles connues et les signalements de compromission de la distribution sont conservés dans le suivi. Une extension privée ou non identifiée, fermée ou sans version exploitable est conservée et signalée explicitement hors couverture ; cela ne constitue pas un certificat d’absence de vulnérabilité. Les thèmes et PHP restent hors du périmètre de mutation et des requêtes à cette API.

Le numéro du paquet est `core-plugins-free-v4`. Toute évolution ultérieure des sources de l’agent doit augmenter ce numéro et conserver les empreintes du paquet précédent pour permettre sa mise à niveau vérifiée.

## Contrôles web depuis Vigie

Les adresses IP des exécuteurs hébergés peuvent être filtrées par o2switch. Les workflows définissent `VIGIE_WORDPRESS_CONTROL_URL` : les contrôles HTTPS et la collecte signée de l’observateur sont alors effectués depuis le serveur Vigie, et les résultats d’inventaire restent dans la base partagée. L’endpoint dédié `/api/maintenance/wordpress` propose trois actions de contrôle bornées (`inventory`, `preflight`, `postflight`) ; il refuse tout domaine fourni par le demandeur et toute installation non éligible. L’appel est signé avec une clé dérivée de la clé de chiffrement existante, lié au corps, au chemin et à un horodatage de 90 secondes. La collecte peut recréer le connecteur d’inventaire autorisé s’il ne répond plus ; elle ne lance aucune mise à jour WordPress et ne retourne aucun secret. Les appels anonymes sont refusés. Les modifications continuent à passer exclusivement par l’agent privé et ses tâches HMAC.
